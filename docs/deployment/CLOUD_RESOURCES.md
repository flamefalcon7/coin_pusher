# ☁️ 云端部署资源需求评估

## 📊 当前架构分析

### 服务器端负载

- **物理引擎**: Rapier (WASM) - CPU 密集
- **游戏循环**: 30Hz (每 33ms 一次 tick)
- **WebSocket**: 实时连接管理
- **消息序列化**: MessagePack 编码/解码

### 客户端

- **静态文件**: React + BabylonJS (CDN/静态托管)
- **无服务器需求**: 纯浏览器运行

## 💻 计算资源需求

### 场景 1: 小规模 (1-50 用户)

#### 单服务器配置

```
实例类型: t3.small 或同等
├─ CPU: 2 vCPU (burstable)
├─ 内存: 2 GB
├─ 存储: 20 GB SSD
└─ 网络: 中等带宽 (1 Gbps)

预估成本:
- AWS EC2 t3.small: ~$15/月
- DigitalOcean Droplet: ~$12/月
- Vultr: ~$12/月
- Railway: ~$5-10/月 (按使用量)
```

#### 性能指标 (单房间 50 用户)

```
CPU 使用率:
├─ 物理引擎 (30Hz): ~25%
├─ WebSocket 管理: ~10%
├─ 消息序列化: ~5%
└─ 系统开销: ~10%
总计: ~50% (峰值 70%)

内存使用:
├─ Node.js 运行时: ~150 MB
├─ Rapier WASM: ~50 MB
├─ 游戏状态: ~10 MB
├─ WebSocket 连接: ~2 MB/用户 (100 MB @ 50 用户)
└─ Buffer/缓存: ~50 MB
总计: ~360 MB (峰值 450 MB)

网络带宽:
├─ 上行: 25 KB/s × 50 = 1.25 MB/s (10 Mbps)
├─ 下行: 5 KB/s × 50 = 0.25 MB/s (2 Mbps)
└─ 峰值: ~15 Mbps

WebSocket 连接:
└─ 50 并发连接 ✅ (单个进程轻松处理)
```

## 🔧 当前架构的限制

### 单服务器限制

```
当前实现:
├─ 单进程 Node.js
├─ 单房间 (所有用户共享)
├─ 无状态持久化
└─ 无水平扩展能力

限制:
├─ WebSocket 连接: ~1000/进程 (理论)
├─ 实际推荐: ~200-500/进程
├─ CPU: 物理引擎瓶颈
└─ 内存: 连接缓冲
```

### 瓶颈分析

#### CPU 瓶颈

```
Rapier 物理引擎:
├─ 30Hz tick @ substeps=2 = 60 次物理计算/秒
├─ 10 硬币: ~5% CPU
├─ 50 硬币: ~25% CPU
└─ 100 硬币: ~50% CPU ⚠️

优化空间:
├─ Sleep 机制 (已启用) ✅
├─ 静态优化 (已优化) ✅
└─ 减少 active bodies (可优化)
```

#### 内存瓶颈

```
每个连接:
├─ WebSocket buffer: ~50 KB
├─ 状态缓冲: ~100 KB
└─ 总计: ~150 KB/用户

200 用户: ~30 MB
500 用户: ~75 MB
1000 用户: ~150 MB

Node.js 堆:
├─ 基础: ~150 MB
└─ 峰值: ~300-500 MB (GC 前)

推荐配置:
├─ 50 用户: 2 GB RAM ✅
├─ 200 用户: 4 GB RAM ✅
└─ 500+ 用户: 8 GB RAM ✅
```

#### 网络瓶颈

```
带宽计算 (MessagePack):
├─ 下行: 25 KB/s × 用户数
├─ 50 用户: 1.25 MB/s (10 Mbps) ✅
├─ 200 用户: 5 MB/s (40 Mbps) ✅
└─ 500 用户: 12.5 MB/s (100 Mbps) ⚠️

连接数:
├─ TCP 端口: 65535 (理论)
├─ 实际限制: ~1000/进程
└─ 推荐: ~200-500/进程
```
