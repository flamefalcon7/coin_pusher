Grounding Context

Codebase Context

即時多人 3D 推幣機：BabylonJS v6.49 客戶端、Rapier 物理（TS game server，15 Hz WebSocket + MessagePack，客戶端 100–500ms 插值緩衝）、Go 後端（NATS relay、PostgreSQL、SUI/USDC 鏈上經濟）。產品四支柱（docs/spec.md）：物理爽感（連鎖瀑布）、多人張力（heat 零和競爭）、策略深度（投幣位選擇）、經濟刺激（變異數）。

既有 juice 基礎設施：VFXManager（池化粒子、combo 偵測、牆面脈動、五種能力特效、幣雨）、SoundManager（Web Audio，5 個取樣音效 + 8 個程序化能力音 + 3 首 BGM、±8–12% 音高隨機化）、卡通渲染 + 靜態後處理（Sobel 描邊、bloom、色差、暗角）、ComboCounter（3 階 CSS 樣式，純裝飾）、slot machine（左牆 50 幣觸發）、jackpot 輪盤（右牆 50 幣）、寶箱（已有依稀有度分階的程序化音效）、megaspeaker。

硬性約束：juice 屬客戶端表現層（不得為伺服器物理參數做客戶端控制）；所有新特效須符合池化 + dispose() 紀律與 count-baseline 洩漏測試（D-003）；表現時序須以插值後的畫面為準，而非伺服器訊息到達瞬間（D-004）；鏈上經濟不得有「把輸包裝成贏」的慶祝（提領信任優先）。外部研究（高價值）：Vlambeer juice 經典、實體推幣機 near-miss 幾何學、賭場音效研究（任何贏都給慶祝音 → 場次 +30%）、gacha 揭示節奏、2025 留存數據（社交功能 D30 26–31%）。

Topic Axes

  1. impact-cascade — 落幣與連鎖瞬間的打擊感（screen shake、hit-stop、粒子、飄字、combo 升級）
  2. anticipation-near-miss — 期待感與「差一點」（邊緣搖搖欲墜、蓄力、推桿節奏預告）
  3. reward-reveal — 獎勵揭示與慶祝（寶箱、jackpot 輪盤、slot、抽獎、彩帶時刻）
  4. audio — 音效層（音高變化、慶祝音、緊張音景 — 制度上全新領域，零既有決策）
  5. multiplayer-spectacle — 多人共感與回訪鉤子（廣播大獎、共同儀表、狂熱狀態）

#1

邊緣劇場（Edge Drama）— 讓「會不會掉？」被看見、被聽見

anticipation-near-miss信心 90%複雜度 Medium
Description
純客戶端的前緣張力表現系統，三層疊加：（a）搖搖欲墜偵測 — 客戶端已持有每枚幣的插值位置（Interpolator.ts 的 knownCoins map），前緣門檻是已知常數（z > 0.7m）；對距邊緣 ~0.1m 內的幣加上依「距離 + 停留時間」漸強的邊緣微光/微顫，掛在邊緣越久的幣越亮 — 全房間每個客戶端會獨立指認出同一批幣，共享注意力自然湧現。(b) 推桿節奏漸強 — 推桿是確定性 0.6 Hz 正弦波，插值後的 pusherZ 每幀可讀；當有幣在懸崖邊時，隨下一次前推衝程逼近播放漸強 tick/微光，衝程頂點正好是「going once…」的拍點。(c) 命定之幣預示 — despawn 訊息比插值畫面早 100–500ms 到達，但目前 removeCoin() 收到訊息立即刪除（GameClient.ts:235 呼叫），造成幣提早消失的視覺 bug；改為收到 despawn 時不刪除，標記為「命定」，在提前量窗口內播放上升 rim-glow + 音效 shimmer，讓緩衝的軌跡把幣可見地帶過邊緣再爆發。零協定變更。

anticipation-near-miss
Basis
direct: Interpolator.ts:20-26「Coins are only removed via removeCoin() (on despawn), so sleeping coins… keep rendering at their last position」；Interpolator.ts:119 targetTime = serverTime - interpolationDelay；CoinOutcome.ts:19 platformFrontZ = 0.05 + 1.3/2 = 0.7m（驗證者已修正原引用行號）；證據 dossier 明確標記「No Near-Miss Feedback Loop — Design intent says 'will it fall?' but mechanic is invisible」對照 docs/spec.md:73-81 的設計意圖。external: 實體推幣機的核心強迫循環正是「特定一枚看得見的懸崖幣」（palm-fun 機構分析）。五個構想 agent 獨立收斂到此方向。

需要為 teeter 訊號設計良好的每幀掃描（幣數多時要做距離預篩）；「命定之幣」延後刪除需小心與後續 state_delta 的一致性；微光強度曲線需要調校避免視覺噪音。

Description

子彈時間（Interpolation Time Magic）— 插值時鐘的時間魔法

impact-cascade信心 70%複雜度 Medium
Description
客戶端渲染的是 targetTime = serverTime - interpolationDelay（Interpolator.ts:119）— 這個時間點是客戶端自己選的數字，背後是一段已緩衝的狀態歷史。把它變成演出工具：hit-stop（爆炸/超級推擊命中瞬間鎖定 targetTime 80–120ms，全世界凍結一拍再緩衝追回）、大瀑布慢動作（插值畫面出現 ≥N 幣 despawn 時渲染時鐘降到 ~0.4x 三四百毫秒，幣以慢動作翻過懸崖，bloom/色差同步尖峰，再以 ~1.15x 追回）、進階版瀑布回放（保留最近 2–3 秒 15Hz delta，超大連鎖結束後以 0.3x 重演一次）。不碰物理、不碰協定 — 純播放速率操作。
Axis
impact-cascade
Basis
direct: Interpolator.ts:117-119（驗證者確認）— 渲染時間是緩衝狀態上的自由變數；dossier 痛點「No hit-stop/freeze frame: No frame pause on major impacts」。external: Vlambeer 經典 — hit-stop 0.1–0.2s 是最重的打擊感工具、保留給巔峰時刻；體育轉播不會全速重播關鍵球。reasoned: 伺服器權威多人遊戲通常做不了 hit-stop，但本作的插值緩衝架構讓它變成純客戶端可行 — 這是別的推幣機 clone 抄不走的差異化。
Rationale
連鎖瀑布是 spec 明言的「核心多巴胺時刻」，目前 2 幣和 40 幣視覺完全等價。時間膨脹是唯一能讓大瀑布「感覺」數量級不同、又零池化/洩漏風險的手段（改的是數字，不是新資源）。觸發本身以插值畫面為準，D-004 由構造保證。
Downsides
開放問題：自適應 100–500ms 緩衝能吸收多少膨脹才不出現追趕僞影 — 需要 30 分鐘白板 + 原型驗證；多人共視下 100ms 凍結「有力」還是「像 lag」是主觀判斷，建議 A/B 開關；回放版需保留 delta 歷史（記憶體小但需設計）。

音階瀑布（Cascade Pitch Ladder）— 聽得見的 combo

audio信心 92%複雜度 Low
Description
despawn 音效管線已支援逐次 playbackRate（SoundManager.ts:124）— 目前餵的是 ±10% 隨機值。combo 窗口內改餵「combo 序號索引的上行五聲音階」：每一波連鎖高一個音，combo 重置時回到根音 — 12 幣瀑布從「一聲悶響」變成一段上行琶音。配套把 200ms 節流（THROTTLE_MS）在連鎖中放寬為 ~70ms 間距的 round-robin 音源池，讓密集瀑布疊出層次而非被丟棄。順手修姊妹問題：程序化能力音每次施放參數完全相同（shock 固定 80→40Hz，SoundManager.ts:168-169），而 shock 是全遊戲最高頻能力（30 次/分）— 把取樣音已驗證的隨機化模式套上去。
Axis
audio
Basis
direct: SoundManager.ts:124 src.playbackRate.value = 1 + (Math.random()*2-1) * pitchRange（管線已在，只是餵噪音不餵意義）；:139,149 節流確認；:168-169 固定頻率確認。external: Peggle「歡樂頌」與彈珠台上行 callout — 街機設計最強的音訊獎勵模式；UBC 賭場研究：贏後慶祝音顯著延長場次。
Rationale
全清單「每行代碼手感增量」最高的一項：~30 行改動、觸碰的是全遊戲最常播放的聲音。audio 軸目前是制度空白，這是建立音訊慣例的最低風險起點，且與 #2 的 audio bus 完全相容。
